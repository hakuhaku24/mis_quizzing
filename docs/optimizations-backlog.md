# 優化待辦（Backlog）

記錄已知但暫緩處理的問題。完成一項就搬進 progress_report。

## 1. AI 批改分數漂移（±1~2 分）— 暫緩，先收集更多案例

**現象**：同一份答案重複批改，分數在 5–7 之間漂移（2026-07-17，microkernel 題實測）。
得分點的認定每次略有不同（同一句話有時進「有答到」、有時進「漏掉」）。

**原因**（依影響大小排序）：
1. **評分基準每次重算**：模型每次批改都要現場把詳解拆成得分點清單，拆法不同 → 覆蓋率算出來就不同。這是漂移的主因。
2. temperature 0.2 非零 + 推理服務本身的非決定性（同 prompt 也可能不同輸出）。
3. 詳解是要點式而非明確的配分表，「部分給分」空間全靠模型裁量。

**解法（按性價比排序）**：
1. **固定 rubric**（治本）：對每題離線跑一次「把詳解拆成 N 個得分點＋配分」，存進 DB（`solutions.rubric` JSON）。批改時把 rubric 直接給模型，只讓它判斷「每個得分點：有/半/無」，分數由程式算。消滅主因，同時讓「有答到/漏掉」的表述穩定。
2. temperature 降為 0。
3. 若仍有殘餘漂移：同一答案批 3 次取中位數（成本 ×3，但單次 <0.01 美元，可接受）。
4. 顯示層：分數旁標註「±1」的不確定性，管理預期。

## 2. System prompt token 開銷

目前批改 prompt 約 900 tokens，每次批改都會送一次。llama-3.3-70b 輸入價 $0.59/M
→ 每次約 0.05 美分，一千次批改約 0.5 美元，**可忽略**。
但原則上 prompt 不宜無限增生：每加一條規則是「每次呼叫都付費 + 模型注意力被稀釋」。
上限抓 ~1500 tokens；超過時優先把規則改成結構化輸出欄位（如 name_checks 的做法）或程式端後處理。
若改用固定 rubric（上面第 1 項），prompt 反而可以大幅精簡。

## 3. 題庫的「複習 vs 測驗」缺口

**現狀**：201 題全部是範本生成題（`school='template'`），零真實考古題。
題目品質可，但定位是「考卷題」：孤立、無鋪墊、詳解是給分要點清單而非教學。
適合診斷（你哪裡不會），不適合補救（教你不會的東西）。

**方向**（待排程）：
- 學習模式：每個知識點先讀 AI 生成的精讀筆記，再進題目
- 錯題教學：批改分數低時一鍵「教我這題」，用漏掉的得分點生成針對性小課
- OCR 真題：裝 Tesseract + chi_tra，抽成大/政大掃描 PDF 的真實考題（風格與深度的 ground truth）
